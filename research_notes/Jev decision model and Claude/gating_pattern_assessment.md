# Fast "System One" classifier as router and tool-call gate around Claude: evidence-based assessment and fit for open-ClaudeOS

Scope: the pattern in the pasted proposal, `[Input] -> fast classifier routes/filters context -> Claude reasons -> fast classifier gates tool calls (auto-execute when P(safe) > 0.85, else escalate to a human or to Claude) and scores outputs against rubrics before publish/commit`. This assesses the pattern itself, whether or not any vendor product exists. Research date: 2026-10-09. Local project context comes from `/home/user/open-ClaudeOS/docs/architecture.md`, `/home/user/open-ClaudeOS/docs/threat-model.md`, `src/claudeos/policy.py`, `src/claudeos/consent.py` and `src/claudeos/planner.py`.

## Security: can a learned classifier used as a tool-call gate be evaded, and does a P(safe) > 0.85 threshold mean anything?

### Takeaway
Yes. Published 2024-2026 research shows that learned detectors and LLM judges are routinely evaded by adaptive attackers. Typical results are >50% to >90% attack success, and up to 100% evasion with character-level tricks, even against defences that originally reported near-zero attack success. The evasion is easiest when the attacker controls text the gate reads. A fixed threshold such as 0.85 carries no security meaning unless the scores are calibrated on the deployment's own data. Guard models are documented as overconfident and as becoming miscalibrated under attack, and an adversary optimises against the score directly.

### Cited Findings
- **Adaptive attacks break most published defences (Oct 10, 2025).** Nasr, Carlini, Tramèr et al., "The Attacker Moves Second": "we bypass 12 recent defenses (based on a diverse set of techniques) with attack success rate above 90% for most", and "the majority of defenses originally reported near-zero attack success rates." The authors argue that evaluating against static attack strings or weak optimisation is flawed. — [arXiv:2510.09023](https://arxiv.org/abs/2510.09023)
- **Indirect prompt injection (IPI) defences for agents (Feb 27, 2025; NAACL 2025 Findings).** Zhan et al. evaluated eight IPI defences for LLM agents and "bypass all of them using adaptive attacks", consistently reaching "an attack success rate of over 50%". The abstract does not say how many of the eight are detection-based. — [arXiv:2503.00061](https://arxiv.org/abs/2503.00061)
- **Guardrail classifiers evaded by character injection and adversarial ML (Apr 15, 2025; rev. Jul 14, 2025).** Hackett et al. tested "six prominent protection systems, including Microsoft's Azure Prompt Shield and Meta's Prompt Guard", "achieving in some instances up to 100% evasion success". Word-importance rankings computed on offline white-box models raise attack success against black-box targets. — [arXiv:2504.11168](https://arxiv.org/abs/2504.11168)
- **An LLM judge that reads attacker content can be told what to decide (Oct 2025).** HiddenLayer bypassed the LLM-judge jailbreak and prompt-injection detectors in OpenAI's Guardrails framework, released with AgentKit on Oct 6, 2025 per secondary coverage. They used the default configuration (gpt-4.1-mini judge, confidence threshold 0.7). A prompt first blocked at 95% judge confidence got through once the attacker fabricated the judge's instructions, including a fake confidence threshold. The same override embedded in fetched web content got a malicious tool call and its output approved. HiddenLayer's stated premise: "if the underlying LLM is vulnerable to prompt injection, the judge LLM is inherently vulnerable." — [HiddenLayer, "Same Model, Different Hat"](https://hiddenlayer.com/research/same-model-different-hat); summarised by [Unite.AI](https://www.unite.ai/hiddenlayer-researchers-bypass-openais-guardrails-exposing-critical-flaw-in-ai-self-moderation/) and [ThreatBeat](https://threatbeat.com/threats/openais-guardrails-can-be-bypassed-by-simple-prompt-injection-attack/). I read the HiddenLayer post only through search summaries, so verify the details against the primary post. I did not check whether OpenAI has since patched the issue.
- **Guard models are miscalibrated, and worse under attack (Oct 14, 2024; ICLR 2025).** Liu et al. evaluated 9 LLM-based guard models on 12 benchmarks. They found "overconfident predictions", "significant miscalibration when subjected to jailbreak attacks", and limited robustness of calibration to outputs from different response models. Temperature scaling, and a proposed contextual calibration when no validation set exists, reduce the miscalibration. — [arXiv:2410.10414](https://arxiv.org/abs/2410.10414)
- **Small classifiers are specified at operating points measured on a dataset, not as absolute probabilities.** Meta reports Llama Prompt Guard 2 as AUC and "Recall @ 1% FPR" (86M: AUC .998, 97.5% recall at 1% FPR on English direct jailbreaks) and as AgentDojo attack-prevention rate "at 3% utility reduction" (86M: 81.2%). The model card warns that "adversaries may develop sophisticated attacks specifically to bypass detection", that "some prompt attacks are highly application-dependent", and that "fine-tuning on application-specific datasets improves performance." — [Llama Prompt Guard 2 model card, Hugging Face (Llama 4 license dated Apr 5, 2025)](https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M)
- **What Prompt Guard 2 actually detects:** "prompts that explicitly try to override prior instructions, regardless of whether the attack would succeed". It is a binary benign/malicious label over a 512-token window. — [model card](https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M)
- **Even a frontier-model gate has double-digit miss rates on real data (Mar 25, 2026).** Anthropic's Claude Code auto mode classifier is an LLM transcript classifier, not a small non-generative model. On real "overeager" actions (n=52) it has a 17% false-negative rate end to end, and 5.7% on synthetic exfiltration (n=1,000), at 0.4% false-positive rate on real traffic (n=10,000). Its Stage 1 alone has 6.6% / 1.8% FNR at 8.5% FPR. Anthropic calls the 17% "the honest number." — [Anthropic Engineering, "How we built Claude Code auto mode" (John Hughes, Mar 25, 2026)](https://www.anthropic.com/engineering/claude-code-auto-mode)
- **Heuristic detection gives no guarantees (Jun 10, 2025).** Beurer-Kellner, Tramèr, Debenedetti et al.: input/output detection defences "remain fundamentally heuristic and cannot guarantee prevention of all attacks". Their principle: once an agent has ingested untrusted input, it must be constrained so that the input cannot trigger consequential actions. — [arXiv:2506.08837 (HTML v3)](https://arxiv.org/html/2506.08837v3)
- **OWASP LLM01:2025:** "it is unclear if there are fool-proof methods of prevention for prompt injection". The listed mitigations include deterministic validation of output formats, least privilege with tool functions kept in application code, "require human approval for high-risk actions", segregating external content, and adversarial testing. Filtering is one item among many. — [OWASP GenAI, LLM01:2025 Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)
- **Anthropic on its own defences (Nov 24, 2025):** "No browser agent is immune to prompt injection." With RL training plus classifiers that scan untrusted content, Anthropic reports a 1% attack success rate against an internal adaptive Best-of-N attacker with 100 attempts per environment, and says this "still carries meaningful risk." — [Anthropic, "Mitigating the risk of prompt injections in browser use"](https://www.anthropic.com/research/prompt-injection-defenses)

### Inferences
- The proposal's gate reads the tool call, and in a context-screening setup also the context. In an agent, tool-call arguments are often derived from attacker-controlled content: an email body, a file path, a URL taken from a fetched page. So the attacker has a channel into the gate's input even when raw tool results are stripped. HiddenLayer's result and the adaptive-attack papers show that this channel is enough to move a learned score.
- "P(safe) > 0.85" means, at best, that the classifier tolerates up to about a 15% chance of an unsafe action per auto-executed call, and only if the scores are calibrated. That is far too permissive for irreversible effects (sending email, HTTP POST). Under attack the number is meaningless, because (a) guard calibration degrades under jailbreaks (Liu et al.) and (b) an adaptive attacker optimises inputs to land above the threshold. Without a held-out, in-distribution, adversarially tested calibration set (reliability diagram, ECE, FNR at the chosen threshold, per action type), the threshold is a guess.
- The base rate matters. Dangerous calls are rare in benign traffic, so a single number like "0.85" hides the operating point that matters: FNR on the rare dangerous class at an FPR users will tolerate. Anthropic reports it in exactly this form (FPR on real traffic, FNR on curated dangerous sets). The proposal gives neither.
- A small, non-generative classifier (DeBERTa-class) asked "is this tool call safe in this context?" is plausibly weaker than Anthropic's Sonnet-class transcript classifier, which still misses 17% of real overeager actions. Prompt Guard 2 is trained for a different task (detecting instruction-override text), not contextual tool-call safety. I found no published small classifier trained and evaluated for contextual tool-call safety, so this inference is unverified.
- "Escalate to Claude for review" is an LLM-judge step. Per HiddenLayer, a judge built on a model that is vulnerable to injection shares that vulnerability, unless the judge's input is restricted (see the next section on how Anthropic strips tool results and assistant prose).

### Gaps
- I found no published calibration study for any tool-call safety gate on agent traffic, and no reliability diagram for Anthropic's auto mode classifier. Anthropic reports FPR/FNR, not calibration.
- I did not obtain per-system evasion numbers from Hackett et al. (only the abstract), nor the list of the 12 defences in Nasr et al. Both need the full papers.
- I could not confirm whether OpenAI changed Guardrails after HiddenLayer's report.

## What do comparable production systems do (Anthropic and others)?

### Takeaway
Production systems layer deterministic rules first (deny > ask > allow, protected paths, critical paths), then an LLM classifier for the residual, uncategorised actions, with fail-closed defaults. They deliberately keep untrusted tool output away from the gate: Claude Code's classifier strips tool results and the assistant's prose, and Managed Agents does not read intent from tool results. Anthropic labels its own classifier-based approval as not a human checkpoint and not a replacement for careful review. Open-source guardrail kits (Prompt Guard 2, LlamaFirewall, NeMo Guardrails) present classifiers as one layer, not the boundary. None of these systems relies on a single fast classifier with a probability cut-off to auto-execute irreversible actions.

### Cited Findings
**Claude Code permission modes and auto mode** (docs fetched 2026-10-09; engineering post Mar 25, 2026)
- In auto mode "a separate classifier model reviews actions before they run, blocking anything that escalates beyond your request, targets unrecognized infrastructure, or appears driven by hostile content Claude read." Warning: "Auto mode reduces permission prompts but does not guarantee safety. Use it for tasks where you trust the general direction, not as a replacement for review on sensitive operations." From v2.1.283 it is the built-in starting mode for interactive terminal and VS Code sessions. — [Claude Code docs: permission modes](https://code.claude.com/docs/en/permission-modes)
- **Fixed decision order, first match wins:** (1) allow/ask/deny rules, with exceptions: protected-path writes still go to the classifier, no allow rule approves critical-path `rm`, and `requiresUserInteraction` MCP tools always prompt; (2) read-only actions and working-directory edits are auto-approved; (3) everything else goes to the classifier; (4) a block returns a reason to Claude. On entering auto mode, broad allow rules that grant arbitrary code execution are dropped (`Bash(*)`, wildcarded interpreters, package-manager run commands). — [permission modes](https://code.claude.com/docs/en/permission-modes)
- **Input restriction as the injection defence:** "the classifier sees user messages, tool calls other than read-only lookups … and your CLAUDE.md content. Tool results are stripped from those requests, so hostile content in a file or web page can't manipulate the classifier directly." "A separate server-side probe scans incoming tool results and flags suspicious content before Claude reads it." — [permission modes](https://code.claude.com/docs/en/permission-modes). The engineering post calls the classifier "reasoning-blind by design": it strips assistant prose and tool outputs and judges what the agent did, not what it said. — [Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)
- **Two stages:** Stage 1 is a fast single-token yes/no filter "instructed to err toward blocking". Stage 2 runs chain-of-thought only on flagged items to cut false positives. The post (Mar 2026) says the classifier ran on Sonnet 4.6. The current docs say it "runs on Claude Sonnet 5 by default rather than on your `/model` selection", so the model has changed since the post. — [Engineering post](https://www.anthropic.com/engineering/claude-code-auto-mode); [permission modes](https://code.claude.com/docs/en/permission-modes)
- **Fail-closed behaviour:** no verdict from the classifier or server leads to denial ("Claude Code denies the action rather than run it unreviewed"). After 3 consecutive or 20 total blocks, auto mode pauses and prompting resumes; these thresholds "are not configurable". Boundaries the user states in conversation ("don't push") are a block signal, but "can be lost if context compaction removes the message … For a hard guarantee, add a deny rule instead." — [permission modes](https://code.claude.com/docs/en/permission-modes)
- **Blocked by default:** examples include `curl | bash`, "sending sensitive data to external endpoints", production deploys, force push, IAM grants, irreversible destruction of pre-existing files, and merging unreviewed PRs. — [permission modes](https://code.claude.com/docs/en/permission-modes)
- **Motivation, approval fatigue:** "Users approve 93% of permission prompts." — [Engineering post](https://www.anthropic.com/engineering/claude-code-auto-mode). A figure that humans catch only 13.6% of dangerous commands versus 89% for the classifier appears only in a French secondary summary. I could not verify it in the primary post, so treat it as unverified. — [search result summary, aiweekly.co](https://aiweekly.co/fr/node/9487)
- **Threat model:** the classifier is tuned mainly for overeager behaviour and honest mistakes. For a misaligned model Anthropic says "We don't currently see this in practice." Auto mode "is not a drop-in replacement for careful human review on high-stakes infrastructure." — [Engineering post](https://www.anthropic.com/engineering/claude-code-auto-mode)

**Claude Code hooks and permission rules (programmatic approval)**
- "Permission rules are enforced by Claude Code, not by the model. Instructions in your prompt or `CLAUDE.md` shape what Claude tries to do, but they don't change what Claude Code allows." — [Claude Code docs: permissions](https://code.claude.com/docs/en/permissions)
- PreToolUse hooks return `permissionDecision` allow/deny/ask/defer and can rewrite input via `updatedInput`. "PreToolUse hook decisions don't bypass permission rules … a matching deny rule blocks the call, and a matching ask rule still prompts even when the hook returned `"allow"`." A hook that exits with code 2 blocks before the rules are evaluated, so it overrides allow rules. — [permissions](https://code.claude.com/docs/en/permissions); [hooks](https://code.claude.com/docs/en/hooks)
- Hooks docs warnings: a timed-out hook "doesn't block the tool call … so don't count on a stalled hook to act as a gate"; "staying silent doesn't approve it"; "If your hook is meant to enforce a policy, use `exit 2`"; the `if` filter is best-effort, so "use the permission system rather than a hook to enforce a hard allow or deny." — [hooks](https://code.claude.com/docs/en/hooks)
- Sandboxing is recommended with permissions "for defense-in-depth, since sandbox restrictions still apply even if a prompt injection bypasses Claude's decision-making." — [permissions](https://code.claude.com/docs/en/permissions)
- A PostToolUse hook can annotate a result with a `classifierContext` field that the auto mode classifier reads as application-provided context (v2.1.236+). This is a sanctioned way to feed trusted metadata, rather than raw tool output, to the gate. — [permission modes](https://code.claude.com/docs/en/permission-modes)

**Claude Managed Agents permission policies** (beta, header `managed-agents-2026-04-01`)
- Policies: `always_allow`, `always_ask`, `auto`. With `auto` "the server evaluates each call and runs it, denies it, or pauses for your approval". ### Inferences
- The closest production analogue to the proposal is Claude Code auto mode or Managed Agents `auto`. They differ from the proposal in four ways: (1) deterministic rules run first and win; (2) the gate is a frontier LLM classifier with restricted inputs, not a fast non-generative model reading everything; (3) failure or uncertainty means deny or ask, never execute; (4) the vendor states that it is not a human checkpoint. The proposal's "auto-execute above 0.85" has none of these properties as stated.
- Anthropic's choice to strip tool results from the gate's input is a direct answer to "the attacker controls content the classifier reads". A proposal that routes or filters context with the same classifier that later gates actions does the opposite: it exposes the gate to the attacker's text.
- The `classifierContext` and `evaluation`/`reason_code` designs show a useful pattern: the gate's verdict is a structured, auditable signal, and trusted metadata reaches it through a separate channel.

### Gaps
- The Anthropic docs do not say what model or classifier backs Managed Agents `auto`, and I found no published error rates for it.
- I found no public evaluation of NeMo Guardrails execution rails or semantic-router thresholds under adaptive attack.
- I did not fetch Llama Guard 4 materials. Llama Guard is a content-safety (harm taxonomy) classifier, not a tool-call safety gate, so it is only tangentially relevant.

## Routing and context screening: what is the evidence on cost, latency and quality trade-offs?

### Takeaway
For model routing (cheap model versus strong model), the evidence is real but benchmark-bound. RouteLLM reported >85% cost reduction on MT Bench at 95% of GPT-4 quality, but only 14% better than random on out-of-distribution MMLU. 2025-2026 work finds simple kNN routers match or beat learned routers, which suggests that much of the claimed gain is in-distribution. For context screening (filtering or flagging retrieved content), evidence exists for security filtering at small utility cost, but I found no rigorous cost or latency studies.

### Cited Findings
- **RouteLLM (Jun 26, 2024; v4 Feb 23, 2025):** routers trained on preference data cut costs "by over 2 times in certain cases-without compromising the quality of responses", and transfer when strong and weak models change at test time. — [arXiv:2406.18665](https://arxiv.org/abs/2406.18665)
- **RouteLLM blog (Jul 1, 2024):** cost reductions versus GPT-4-only of >85% on MT Bench, 45% on MMLU and 35% on GSM8K, at 95% of GPT-4 performance. Data augmentation was critical. On MMLU, routers trained only on Arena data were "near random" (out-of-distribution). Adding about 1,500 golden-label samples (under 2% of training data) helped, but the best MMLU router still needed 54% GPT-4 calls, "only 14% cheaper than the random baseline". The router types were similarity-weighted ranking, matrix factorization, a BERT classifier and a causal LLM classifier. — [LMSYS blog](https://www.lmsys.org/blog/2024-07-01-routellm/)
- **kNN versus learned routers (May 2025):** a well-tuned kNN "not only matches but often outperforms state-of-the-art learned routers", attributed to locality of model performance in embedding space. The paper notes that disparate training data and evaluation setups make comparison and generalisation difficult. — [arXiv:2505.12601](https://arxiv.org/abs/2505.12601v1)
- **"The Routing Plateau":** kNN is among the leading methods on every benchmark, and learned routers show no clear advantage on hard queries. — [arXiv:2606.07587](https://arxiv.org/pdf/2606.07587). I could not confirm the venue or date; the ID suggests Jun 2026.
- **Counterpoint, Router-R1 (Jun 2025):** an LLM-as-router trained with RL "significantly surpasses" router baselines including kNN, and generalises to unseen models via model descriptors. This uses an LLM, not a fast classifier. — [arXiv:2506.09033](https://arxiv.org/abs/2506.09033)
- **RouterBench (Mar 2024)** is an earlier benchmark that already used kNN baselines. — [arXiv:2403.12031](https://arxiv.org/abs/2403.12031)
- **Context screening for security:** Prompt Guard 2 86M prevented 81.2% of AgentDojo attacks at a 3% utility reduction (22M: 78.4%). — [model card](https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M). Anthropic's server-side probe scans tool results and adds a warning that tells the agent to "treat the content as suspect and re-anchor on the user's request". It does not silently drop content. — [Engineering post](https://www.anthropic.com/engineering/claude-code-auto-mode)
- **Vendor positioning, current lineup:** Claude Haiku 5.5 is described as "for high-volume, latency-sensitive tasks such as classification, extraction, and routing", priced from $0.10/$0.50 per MTok input/output, against Sonnet 5.5 at $2/$10 and Opus 5.5 at $4/$20. — [Claude models overview](https://platform.claude.com/docs/en/about-claude/models/overview)

### Inferences
- In an agent OS the "cheap versus strong model" choice has a quality floor. A misrouted planning task produces a worse plan, which the human then has to catch at the approval card. Routing errors therefore turn into approval burden, not just answer quality. RouteLLM's out-of-distribution MMLU result suggests that a router trained on generic data will be weak on one person's own intent distribution until it is trained on their data.
- Silent context filtering (dropping retrieved chunks the classifier dislikes) has two failure modes: false negatives let injected text through, and false positives remove legitimate evidence, which degrades plans in ways the user cannot see. Anthropic's choice to flag rather than drop, and to warn the agent, seems a better fit for a transparent-consent system.
- The cost argument for a separate fast classifier is weaker in 2026 than in 2024, because small hosted LLMs now target classification and routing at very low per-token prices. The choice between a DeBERTa-class model and a small LLM is mostly about latency, offline operation and privacy, which matter for open-ClaudeOS's local model router, not about cost.

### Gaps
- I found no rigorous, recent (2025-2026) study that measures end-to-end cost, latency and quality for retrieval or context filtering in front of an agent. The available numbers are routing-only (RouteLLM and successors) or security-only (AgentDojo utility drop).
- I found no evidence on rubric-based output scoring as a pre-publish gate (precision, recall, or susceptibility to injection). The HiddenLayer result suggests output judges share the injection problem.
- I found no evidence on intent-routing accuracy for desktop or OS intents specifically.

## Where is a fast classifier genuinely useful in an agent OS, and where must it never be the sole control?

### Takeaway
A fast classifier helps where errors are cheap, visible or reversible: intent triage and routing, ranking and retrieval, flagging suspicious content, ordering and highlighting risk on an approval card, and proposing standing rules that a human then confirms. It must never be the sole control for irreversible or external effects, for access to secrets or protected paths, or for anything an attacker can influence through content the classifier reads. Anthropic's own approval gate misses 17% of real dangerous actions, so the consent decision must rest on deterministic policy and plan-bound human approval.

### Cited Findings
- Approval fatigue is real and measured: users approve 93% of permission prompts. — [Anthropic Engineering, Mar 25, 2026](https://www.anthropic.com/engineering/claude-code-auto-mode). The open-ClaudeOS threat model also lists approval fatigue as a threat ("Frequent prompts teach people to approve without reading"). — `docs/threat-model.md`
- Even Anthropic scopes its classifier gate to reversible, in-scope work. Working-directory edits skip the classifier entirely (deterministic tier). External sends, deploys and destructive operations are blocked by default. "For a hard guarantee, add a deny rule instead." — [permission modes](https://code.claude.com/docs/en/permission-modes)
- Managed Agents: "`auto` is not a human checkpoint … If a person must review a tool's calls before they run, configure `always_ask`." — [permission policies](https://platform.claude.com/docs/en/managed-agents/permission-policies)
- OWASP LLM01:2025 recommends human approval for high-risk actions and least privilege in application code. — [OWASP](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)
- The design-pattern literature (Plan-Then-Execute, Action-Selector, Dual LLM, Context-Minimization and others) constrains what untrusted input can cause, rather than detecting it. — [arXiv:2506.08837](https://arxiv.org/html/2506.08837v3)
- Classifier latencies are compatible with interactive use: Prompt Guard 2 takes 19-92 ms per 512-token segment on an A100. — [model card](https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M)

### Inferences
- **Genuinely useful (advisory, fail-safe direction):**
  - *Intent triage and routing:* local versus cloud model, which planner prompt or toolset to load, offline fallback. Errors cost quality or latency, not safety, provided the policy engine still gates the result.
  - *Ranking and retrieval* in the context service: ordering search results. Prefer flagging over dropping.
  - *Suspicious-content flagging:* mark a read file as "contains instruction-like text" on the card and warn the planner. This adds friction only.
  - *Risk highlighting on the approval card:* sort actions, expand the riskiest by default, add a labelled "classifier note".
  - *Approval-fatigue reduction, indirectly:* mine approval history to *suggest* standing rules that a human confirms and deterministic code then enforces.
  - *Quality checks:* rubric scoring of drafts as a hint to the planner to revise before the plan reaches the card.
- **Never the sole control:** irreversible or external effects (mail, HTTP, calendar invites, publishing); reads or writes of protected paths and secrets; recipient or host trust; anything where the classifier's input includes attacker-influenced text and its output can *reduce* friction; and output rubric scoring as the go/no-go for publish or commit.
- The key design rule is asymmetry: a learned signal may *add* friction (escalate, warn, expand detail) but may never *remove* a deterministic requirement. With this rule, an attacker who fools the classifier at worst gets the baseline deterministic behaviour, not a bypass.

### Gaps
- I found no empirical study of whether classifier risk badges on approval UIs improve human detection rates or instead induce over-trust (automation bias) in agent consent dialogs. This should be user-tested.

## Is `claude-3-5-sonnet-20241022` still available as of 2026-10-09, and what is a current equivalent?

## How could open-ClaudeOS use such a classifier without violating its principles, and what must stay deterministic?

### Takeaway
It fits as an advisory and routing component: intent routing in the existing "Model router", risk highlighting on the approval card, injection flagging on read content, and standing-rule *suggestions*. It may only ever add friction. It must not decide or downgrade risk, skip consent for external effects, or auto-approve plans. Approval and denial, effect class, risk floors, protected paths, recipient and host trust, grant digests, TOCTOU checks and the audit trail stay in deterministic code. The proposal's "auto-execute when P(safe) > 0.85" directly contradicts principle 1 ("The model proposes; deterministic code decides") and principle 2 (plan-bound consent). The architecture doc already rejected the same idea in its original form ("Constitutional guardrails that evaluate semantic intent decide whether actions run" was replaced because "A model judging intent can be talked out of its judgment").

### Cited Findings
- **Project principles:** "A language model is never the security boundary … Whether an action is allowed, how risky it is, and whether it runs are decided by code that no prompt can argue with." "A plan is the unit of consent." "What you approve is rendered from the actions, not from model prose." — `docs/architecture.md`
- **Existing slot for a fast model:** "Model router. A small local model handles fast, simple work: classifying intents, routing, autocomplete in the Intent Bar, offline fallback." — `docs/architecture.md`
- **Deterministic risk today:** `policy.py` states "No model is consulted here." `Risk` is LOW (new files), MEDIUM (changes or removes existing files, undoable) or HIGH (leaves the machine, cannot be undone). External actions are always HIGH. `consent.render_card` prints each action with policy notes, labels the model's summary "(its own words)", and prints "Overall risk" as the max of the deterministic assessments. — `src/claudeos/policy.py`, `src/claudeos/consent.py`
- **Known gaps a classifier could help with (advisory):** taint tracking from `read_file` to external payloads (planned); secrets in ordinary files ("Path-name heuristics … a token pasted into `notes.md` [is] not detected"); and "No standing policy yet … every plan prompts, which will cause approval fatigue." — `docs/threat-model.md`
- **External precedent for each element:**
  - Restricting the gate's inputs (no tool results, no assistant prose). — [Claude Code permission modes](https://code.claude.com/docs/en/permission-modes); [Engineering post](https://www.anthropic.com/engineering/claude-code-auto-mode)
  - Flagging rather than dropping suspicious tool output. — [Engineering post](https://www.anthropic.com/engineering/claude-code-auto-mode)
  - Structured, auditable verdicts (`evaluated_permission`, `reason_code`). — [Managed Agents](https://platform.claude.com/docs/en/managed-agents/permission-policies)
  - Deny rules that no hook or classifier can override. — [Claude Code permissions](https://code.claude.com/docs/en/permissions)
  - Plan-Then-Execute, where the plan is fixed before untrusted data can change it. — [arXiv:2506.08837](https://arxiv.org/html/2506.08837v3)

### Inferences
**Concrete, principle-compatible uses (ordered by value and safety)**
1. **Intent routing (Model router):** a local classifier, or `claude-haiku-5-5` when online, picks the planner model and effort, the toolset, and the workspace scope suggestion. It is safe because the plan still goes through `Policy.assess` and consent. Train or tune it on the user's own logged intents, since RouteLLM shows out-of-distribution routers fall to near random. Log the route in the audit log.
2. **Advisory risk signal on the approval card:** add a separate, clearly labelled line per action (for example "Classifier note (advisory): unusual recipient for this workspace; text resembling instructions found in `invoices/2026-09-initech.txt`"). Hard rule: the displayed "Overall risk" stays `max(deterministic)`. The classifier may *raise* the presentation (expand the action, require scrolling through the outbound body, add a typed confirmation) but never lower `Risk`, never hide details and never collapse the card.
3. **Injection and secret flagging on reads:** run a Prompt-Guard-class detector over `read_file` results and the planned outbound payloads. Use hits to (a) warn the planner, as Anthropic's probe does, (b) annotate the card's "files read while planning" list, and (c) mark candidate taint for the planned deterministic taint tracker. Never use a *miss* as evidence of safety.
4. **Standing-rule suggestions to cut approval fatigue:** mine the audit log for repeated approvals (for example "always approved new files under `~/reports`") and propose a rule. The human approves the rule itself on its own card. The rule is then enforced by deterministic `Policy` code, scoped to LOW and local, reversible effects (new files, possibly undoable edits). External effects are never eligible. This addresses the "No standing policy yet" gap without letting a model approve anything.
5. **Pre-card quality check:** rubric scoring of drafted file content or email text can trigger a planner revision before the card appears. It is never a publish or commit gate, and never shown as a safety score.

**Must stay deterministic (non-negotiable under the project's principles)**
- Allow/deny of every action. A denied action refuses the whole plan.
- The effect class (local versus external) and the risk floor: external is always HIGH and always needs explicit consent.
- Protected paths, workspace scoping and symlink checks.
- Trusted recipient domains and hosts.
- Size limits.
- Grant minting and digest binding, and the expiry.
- The commit-time TOCTOU refusal and the undo journal.
- The audit log.
- Standing-rule *enforcement*: rules are data that deterministic code matches, never a classifier score.
- The asymmetry rule itself: a classifier output can only escalate.

**What to avoid from the proposal**
- **No P(safe) > threshold auto-execution.** If auto-execution of local, reversible actions is ever wanted, it should come from deterministic standing rules plus the undo journal, not from a probability.
- **The gate classifier must not read tool results or file contents if its verdict can reduce friction.** If it does read them (for flagging), its output must be advisory only.
- **"Escalate to Claude for review" must not replace human consent for external effects.** A second Claude pass reads the same attacker-controlled text and inherits the same injection exposure (HiddenLayer). Anthropic avoids this only by stripping inputs, and still reports a 17% FNR.

**If a classifier signal is shown, how to validate it**
- Measure FNR and FPR per action type on the project's own logged plans, including the `examples/invoices-demo` injection case and an adaptive red-team set (per Nasr et al.: attack the defence, not static strings).
- Report calibration (reliability, ECE) before showing any number. Prefer categorical badges ("unusual", "instruction-like text found") over a raw probability, which users will read as a guarantee.

### Gaps
- Whether a risk badge on the card reduces or worsens approval fatigue and over-trust in practice is untested. I found no study for agent consent UIs.
- No dataset of real open-ClaudeOS plans exists yet (Phase 0) to train or calibrate a classifier. Any threshold chosen now would be uncalibrated by construction.
- I did not evaluate specific local models for the Model router (size, latency on CPU, licence). That needs a separate benchmarking task.
