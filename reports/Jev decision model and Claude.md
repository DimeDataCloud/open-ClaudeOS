# Use Jev to route, never to approve

Jev is real. TypeSafe AI launched it on 15 September 2026 as a "System One" decision model. It answers typed questions (a choice, a score, or a yes/no question TypeSafe calls a "noul") with probabilities and never generates text. It costs **$0.042 per million input tokens, output is free, and most calls take about 100 ms**. The pasted description gets that concept right, along with the "noul" type and both SDK package names. Nearly every mechanical detail is wrong. The TypeScript example would fail before it sent a request (wrong class, wrong method, wrong field names, missing required question text), and it targets `claude-3-5-sonnet-20241022`, a Claude model **retired on 28 October 2025**. "Under 300 ms" appears nowhere in TypeSafe's material, which gives 70–500 ms end to end. The ecosystem items all exist, but most do less than the description says. jev-gateway *picks* tools rather than approving them, and with Claude Code it can only add a hint. The TypeSafe plugin is a documentation skill, and every "jev-mcp" server is community code. On the design question the evidence splits cleanly. A fast decision model is a good router and a useful source of warning flags. An auto-execute gate at P(safe) > 0.85 has no defensible meaning: adaptive attacks push learned detectors past 90% evasion, TypeSafe lists adversarial content as a Jev weakness, and even Anthropic's frontier-model gate misses 17% of real overeager actions. For open-ClaudeOS, Jev therefore fits only in the place the project has already set aside for it. It can route intents and add friction to the approval card, under a hard rule that a learned score may escalate a decision but never relax one.

## Jev is a three-week-old model that sells probabilities, not prose

TypeSafe AI is a San Francisco lab that came out of stealth with Jev, which it calls "the first public System One Model … optimized for automation". Its tagline: "LLMs produce words for people. Jev produces typed decisions." ([typesafe.ai](https://typesafe.ai)). The docs are explicit that **"Jev evaluates typed questions against a state and returns structured results directly. No text generation, no parsing."** ([TypeSafe docs](https://docs.typesafe.ai/introduction.md)). The name comes from Kahneman's fast, intuitive System One ([TypeSafe docs: System One](https://docs.typesafe.ai/concepts/system-one.md)). TypeSafe also warns that Jev "is **not** a drop-in replacement for the LLM behind Claude Code, Cursor, opencode, Copilot" ([TypeSafe docs: coding agents](https://docs.typesafe.ai/introduction/coding-agents.md)). The company credits a new training method, Reinforcement Learning for Calibrated Decisions (RLCD) ([typesafe.ai](https://typesafe.ai)). Press coverage, not TypeSafe's own pages, gives the rest. TypeSafe was founded in 2024, its CEO Diogo Almeida is a former OpenAI researcher, and VKTR reports a **$40M seed round led by DCVC** ([VKTR](https://www.vktr.com/ai-platforms/chatgpt-cocreator-launches-typesafe-ai-with-jev/)).

The API is small. A single endpoint, `POST https://api.typesafe.ai/v1/systemone`, takes a `state` (a string, JSON object or array), a `model` and a map of named `questions`. It returns `answers` under the same keys ([API reference](https://docs.typesafe.ai/api.md)). There are exactly three question types. A **Choice** picks one of up to 255 labelled options and returns `choice`, `probabilities` and `confidence`. A **Score** rates the state on 2–10 ordered levels and returns an interpolated score. A **Noul** is a yes/no question whose whole answer is one number, the probability of "yes", with no separate confidence field ([Noul docs](https://docs.typesafe.ai/primitives/noul.md)). The current model is `jev-1.13.0`, and the aliases `jev-latest` and `jev-preview` both point to it ([Models](https://docs.typesafe.ai/models.md)). A request is capped at **64k tokens, and the state plus the longest single question at 32k**. Input is text only, English works best, rate limits are 100K tokens/s and 80 requests/s and "can change without notice", and Jev is not trained on customer data. Zero data retention is offered only to enterprise customers ([Models](https://docs.typesafe.ai/models.md)).

The performance claims need discounting. The homepage advertises **"193.6x Faster, 444.6x Cheaper"** and "Zero Hallucinations", but its own chart values (0.114 s against 8.566 s, $0.000081 against $0.013880) work out to roughly 75x and 171x ([typesafe.ai](https://typesafe.ai)). The launch post adds three caveats. Accuracy was scored as agreement with the average of GPT-6 Astra and Fable 5.1, not against ground truth. The multipliers sit "on the higher end of real world gains". The zero-hallucination claim "is not empirical" and rests only on guaranteed schema matching ([launch post](https://typesafe.ai/blog/introducing-system-one-models-and-jev)). VKTR notes that **"no independent evaluation has confirmed these claims"** ([VKTR](https://www.vktr.com/ai-platforms/chatgpt-cocreator-launches-typesafe-ai-with-jev/)). TypeSafe publishes no calibration metric such as ECE or Brier score, and its docs concede that "calibration is measured across groups of predictions; it does not guarantee that an individual answer is correct" ([System One](https://docs.typesafe.ai/concepts/system-one.md)). Its own list of Jev 1.13 weaknesses includes literal reading, counting, date comparison, indirection, large irrelevant state, **adversarial content**, contradictory criteria and sensitivity to the order of Choice options ([Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md)). That list matters for the gating question below.

## The pasted description blends real sources into code that cannot run

At the level of concept, the description holds up. Jev is decision-only. The three types are choices, scores and yes/no "noul" questions; the name is TypeSafe's own coinage and its origin is undocumented ([TypeSafe llms.txt](https://docs.typesafe.ai/llms.txt)). Both package names are correct: `@typesafe-ai/sdk` 0.6.0 on npm ([npm](https://registry.npmjs.org/@typesafe-ai/sdk)) and `typesafe-sdk` 0.7.2 on PyPI ([PyPI](https://pypi.org/pypi/typesafe-sdk/json)). The latency claim does not hold up. TypeSafe gives three different numbers: "about 100 ms" for most queries ([How to build](https://docs.typesafe.ai/concepts/how-to-build-with-system-one)), "150ms" for real-time use ([use cases](https://docs.typesafe.ai/concepts/use-case-map)), and **"70ms-500ms" end to end, measured from West Coast laptops** ([launch post](https://typesafe.ai/blog/introducing-system-one-models-and-jev)). Cookbook runs averaged 111–114 ms ([Noul cookbook](https://docs.typesafe.ai/cookbooks/consistency_noul_cookbook.md)). "Usually well under 300 ms" is fair. "Under 300 ms" as a property of the model is not, and no percentile or SLA is published.

### The TypeScript example fails on its first line

The example's errors are not random. Two of its wrong names come from Vercel's AI SDK, which wraps Jev under different terms. The AI SDK's function was `experimental_evaluate`, and its yes/no answer field is `probability` ([Vercel Docs: Decision](https://vercel.com/docs/ai-gateway/modalities/decision)). TypeSafe's own SDK uses `systemOne` and `noul`. The snippet joins half of each API, and `options` exists in neither. That looks like an LLM blending two real sources.

| Pasted code | What `@typesafe-ai/sdk` 0.6.0 actually exposes | Verdict |
|---|---|---|
| `new TypeSafe({ apiKey })` | `new TypeSafeClient()`; `apiKey` is a real option and falls back to `TYPESAFE_API_KEY`. Nothing named `TypeSafe` is exported ([index.ts](https://github.com/typesafe-ai/typesafe-sdk-js/blob/v0.6.0/src/index.ts)) | Wrong class |
| `jev.evaluate({...})` | `client.systemOne({...})`; the model is a `model` string, not a separate object ([client.ts](https://github.com/typesafe-ai/typesafe-sdk-js/blob/v0.6.0/src/client.ts)) | Wrong object and method |
| `state: {...}` | `state` (string, object or array) | Correct |
| `is_safe: { type: 'noul' }` | `type: "noul"` is right, but the HTTP API marks `instructions` as **required**. The key `is_safe` is never sent to the model, so as written Jev is not told what to judge ([API reference](https://docs.typesafe.ai/api.md)) | Missing the question |
| `action_type: { type: 'choice', options: [...] }` | `criteria` is a **map** of label to description; the `choice()` helper throws on arrays ([questions.ts](https://github.com/typesafe-ai/typesafe-sdk-js/blob/v0.6.0/src/questions.ts)) | Wrong field and shape |
| `answers.is_safe.probability` | `answers.is_safe.noul`; no TypeSafe answer has a `probability` field ([types.ts](https://github.com/typesafe-ai/typesafe-sdk-js/blob/v0.6.0/src/types.ts)) | Returns `undefined` |

The corrected shape below is assembled from the documented v0.6.0 signatures and has not been executed. It fixes the API calls but not the decision logic around them, which the later sections argue against.

```ts
import { choice, noul, TypeSafeClient } from "@typesafe-ai/sdk";

const client = new TypeSafeClient(); // reads TYPESAFE_API_KEY
const res = await client.systemOne({
  model: "jev-latest",
  state: { intent, tool: call.name, input: call.input },
  questions: {
    is_safe: noul("Does this tool call stay within what the user asked for?"),
    action_type: choice("What effect does this call have?", {
      read_only: null, local_write: null, external: "sends data off the machine",
    }),
  },
});
const pYes = res.answers.is_safe.noul;          // 0..1, no separate confidence
const kind = res.answers.action_type.choice;    // plus .probabilities and .confidence
```

The Claude half of the example is also broken. Anthropic retired `claude-3-5-sonnet-20241022` on **28 October 2025**, and "requests to retired models will fail". The listed replacement is `claude-sonnet-4-6` ([model deprecations](https://platform.claude.com/docs/en/about-claude/model-deprecations)). Today's choices are `claude-opus-5-5` (Anthropic's recommended default, and already open-ClaudeOS's default in [planner.py](../src/claudeos/planner.py)), `claude-sonnet-5-5`, or `claude-haiku-5-5` for "classification, extraction, and routing" ([models overview](https://platform.claude.com/docs/en/about-claude/models/overview)). Code from 2024 needs more than a model-ID swap. On Claude 4.7 and later, non-default `temperature`, `top_p` and `top_k` return a 400 error, and `budget_tokens` thinking has been replaced by adaptive thinking with `effort` ([model deprecations](https://platform.claude.com/docs/en/about-claude/model-deprecations)).

## A P(safe) > 0.85 auto-execute gate fails on the evidence

Even in the best case, the threshold promises little. If Jev's scores were perfectly calibrated, an auto-executed call scored at 0.86 would still be unsafe about 14% of the time. And no published calibration data exists to say they are calibrated. A Noul's number is P(yes) to whatever question was asked, so "P(safe)" is only as meaningful as the wording. Vercel's own guidance is to **calibrate cutoffs on your own labelled data**. Its illustration shows a 0.80 cutoff sending 5% of automatic routes to the wrong place, and a 0.95 cutoff cutting that to 1% while sending 600 of 1,000 items to review ([Vercel: thresholds](https://vercel.com/i/jev-probabilities-and-thresholds)). The template's 0.95 and the gateway docs' 0.6 are labelled starting points for routing form submissions ([Decision Fallbacks](https://vercel.com/docs/ai-gateway/models-and-providers/decision-fallbacks)). They are not security thresholds. An error rate of that order would be acceptable for sorting support tickets. It is not acceptable for sending email.

Under attack, the number means even less. **Nasr, Carlini, Tramèr et al. bypassed 12 recent defences with attack success above 90% for most**, though most had originally reported near-zero attack success ([arXiv:2510.09023](https://arxiv.org/abs/2510.09023)). Zhan et al. beat all eight indirect-injection defences for agents at over 50% success ([arXiv:2503.00061](https://arxiv.org/abs/2503.00061)). Hackett et al. reached **up to 100% evasion** against Azure Prompt Shield and Meta's Prompt Guard ([arXiv:2504.11168](https://arxiv.org/abs/2504.11168)). Guard models are also overconfident, and their calibration degrades specifically under jailbreak ([arXiv:2410.10414](https://arxiv.org/abs/2410.10414)), so a fixed cutoff stops meaning anything at the moment it matters most. HiddenLayer showed how directly a judge can be steered. They got past OpenAI's LLM-judge guardrail by fabricating the judge's instructions, including a fake confidence threshold, inside attacker content ([HiddenLayer](https://hiddenlayer.com/research/same-model-different-hat)). That result was read through summaries and should be checked against the primary post. In an agent, tool-call arguments are routinely derived from attacker-controlled text: a recipient taken from an invoice, a URL from a fetched page. A gate that reads those arguments therefore gives the attacker a channel into its input. TypeSafe's own list of known Jev weaknesses includes adversarial content.

Production systems are built the other way round. Claude Code's auto mode applies deterministic allow/ask/deny rules first. Its classifier is a Sonnet-class model that **never sees tool results or assistant prose**, "so hostile content in a file or web page can't manipulate the classifier directly", and if no verdict arrives the action is denied ([permission modes](https://code.claude.com/docs/en/permission-modes)). Even so, Anthropic reports a **17% false-negative rate on real overeager actions** and 5.7% on synthetic exfiltration, at a 0.4% false-positive rate, and calls 17% "the honest number" ([Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)). The docs add that auto mode "does not guarantee safety" ([permission modes](https://code.claude.com/docs/en/permission-modes)). Managed Agents is blunter: **"`auto` is not a human checkpoint"**, and any tool whose calls a person must see should be set to `always_ask` ([permission policies](https://platform.claude.com/docs/en/managed-agents/permission-policies)). OWASP recommends human approval for high-risk actions and keeping tool permissions in application code ([OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)). The design-pattern literature concludes that detection "cannot guarantee prevention", and that untrusted input must be structurally unable to trigger consequential actions ([arXiv:2506.08837](https://arxiv.org/html/2506.08837v3)).

The proposal's fallback, "escalate to Claude for review", does not close the gap either. A second Claude pass reads the same attacker-influenced text and inherits the same injection exposure; Anthropic avoids this only by stripping the gate's inputs. A design in which the same fast model also filters context makes the problem worse, because the gate then reads exactly the text the attacker wrote. A defensible version of the gate would need three things: false-negative and false-positive rates measured per action type on the deployment's own traffic, an adaptive red team rather than static attack strings, and a scope limited to reversible local actions. Once the scope is limited that far, deterministic rules plus an undo journal do the job better and need no probability at all.

## Routing is where a fast decision model earns its place

Routing errors cost quality, not safety, as long as a policy layer still gates whatever the routed model proposes. That makes routing the natural job for Jev. The general evidence on routing is real but bounded by benchmarks. RouteLLM cut costs by **over 85% on MT Bench at 95% of GPT-4 quality**. Out of distribution on MMLU its routers were "near random", and the best still needed GPT-4 for 54% of calls, only 14% cheaper than random ([LMSYS](https://www.lmsys.org/blog/2024-07-01-routellm/)). A well-tuned kNN router matches or beats learned routers ([arXiv:2505.12601](https://arxiv.org/abs/2505.12601v1)). In practice, **a router has to be tuned on its own traffic**, which for a personal agent OS means one person's intents.

The Jev-specific routing patterns are well documented. TypeSafe describes intent routing to "deterministic logic, a specialist LLM, or a human" and a guardrail cookbook that thresholds hazard scores to "pass, review, block, or route" ([TypeSafe llms.txt](https://docs.typesafe.ai/llms.txt)). Vercel's form-router template accepts Jev's answer only above 0.95 confidence. Otherwise it hands the same question to a stronger model, with explicit reasons for low confidence, missing confidence and Jev errors ([KB guide](https://vercel.com/kb/guide/jev-ai-sdk-form-router)). AI Gateway now offers the same escalation declaratively through `confidenceBelow` conditions ([Decision Fallbacks](https://vercel.com/docs/ai-gateway/models-and-providers/decision-fallbacks)). That pattern is the right one: low confidence buys more scrutiny, never less.

Routing *inside* Claude's tool loop shows the limits. jev-gateway's self-reported medians (five runs per cell) favour bug-fixing. For Sonnet 5 in Claude Code it cut **output tokens by 41% and wall time by 25%**. On feature tasks it made Opus 5 **83% slower** and Sonnet 5 37% slower, and it adds roughly 0.5–1 s per tool-bearing turn ([jev-gateway README](https://github.com/vinilana/jev-gateway/blob/main/README.md)). Steering an agent mid-loop fights the harness: thinking, caching and a tool list of about 280 entries. Routing *before* the agent starts (which model, what effort level, which toolset) avoids all three. On cost, Jev at $0.042/M input with free output is cheaper than Claude Haiku 5.5 at $0.10/$0.50 ([models overview](https://platform.claude.com/docs/en/about-claude/models/overview)). At agent-OS volumes the difference is negligible. By my arithmetic from those list prices, a 2,000-token routing call costs about $0.00008 on Jev and $0.0002 on Haiku, against roughly $0.08 for a 20,000-token Opus 5.5 planning turn. Jev's real advantage is speed. TypeSafe's cookbook measured it at about 110 ms against 1.0–3.9 s for claude-haiku-4-5 ([Choice cookbook](https://docs.typesafe.ai/cookbooks/consistency_choice_cookbook.md)), a vendor-run comparison against an older Haiku. That gap matters for an interactive Intent Bar, and it does not matter for safety.

## open-ClaudeOS already reserved the right slot: escalate, never relax

The project settled the principle before Jev existed. Its architecture replaced "constitutional guardrails that evaluate semantic intent" with deterministic policy because **"a model judging intent can be talked out of its judgment"** ([architecture.md](../docs/architecture.md)). `policy.py` opens with "No model is consulted here" ([policy.py](../src/claudeos/policy.py)). The permission-fatigue plan already states that fast classifiers "stay advisory … It never becomes the thing that decides an action may run unseen" ([challenges.md](../docs/challenges.md)). The roadmap lists Jev as an open question about "where they must not be used" ([roadmap.md](../docs/roadmap.md)). An auto-execute gate at 0.85 contradicts principle 1 (deterministic code decides) and principle 2 (consent is a person's approval, bound to the digests of the exact actions). Under that gate, a score rather than a grant would decide that an action runs.

The **asymmetry rule** is what makes Jev safe to adopt: a learned signal may add friction but never remove a deterministic requirement. It also changes Jev's engineering requirements. If Jev can only escalate, then a timeout, a 429, a 529 "overloaded" response or a successful adversarial input all fall back to today's card and policy, which is already safe. Jev then needs no SLA and no fail-closed logic, and a calibration error costs attention, not safety. A real gate is the opposite case: it must fail closed, so Jev's availability, whose rate limits "can change without notice", would become part of the security story.

| Use in open-ClaudeOS | What Jev reads | Allowed effect | If Jev is wrong or fooled |
|---|---|---|---|
| Intent routing in the Model router | The intent text only | Picks planner model, effort and toolset; logged | A weaker plan, caught at the card |
| Flagging injection-like text in `read_file` results | File contents | Warns the planner; annotates "files read while planning"; never drops content | A miss leaves the deterministic baseline unchanged |
| Highlighting unusual actions on the card | Typed actions plus the list of reads | Expands an action, adds a labelled "advisory" note, can require typed confirmation | A false alarm adds friction; a miss leaves the normal card |
| Paraphrased-exfiltration hints alongside taint tracking | Outbound body plus read excerpts | Adds a card flag next to the deterministic taint result | A false alarm adds friction; a miss leaves the deterministic result |
| Suggesting standing rules from the audit log | Approval history | Proposes a rule the person approves on its own card, enforced afterwards by `Policy` code | The person rejects a bad suggestion |
| Rubric check on drafts | Draft text | Triggers a planner revision before the card appears | Lower quality, no safety impact |
| Auto-execute when P(safe) > 0.85 | Tool calls | **Rejected** | An unapproved, possibly irreversible effect |

In code, this becomes an advisor step after `Policy.preview`. It appends clearly labelled notes beneath the deterministic ones in `render_card`. `plan_risk` stays the maximum of the deterministic assessments ([consent.py](../src/claudeos/consent.py)). Grants keep hashing the actions, not the advice, and the audit log records the model version Jev returns (for example `jev-1.13.0`) alongside its answers. One test pins the invariant. With the advisor stubbed to return any possible output, the set of denials and the grant digests must stay identical, and the advisor may only add notes or raise the presentation level. The Python SDK (`typesafe-sdk`, Python ≥ 3.10, matching the project's `requires-python`) fits as an optional extra next to `claude`. Its phasing matches the roadmap. Read flagging, taint hints and rule suggestions belong in Phase 1 alongside taint tracking and standing rules. Card highlighting belongs in Phase 2 with "cards that show what is unusual" ([roadmap.md](../docs/roadmap.md)).

Two mismatches need a decision first. Jev is a hosted API, and nothing in the research shows local weights, so it cannot be the architecture's "small local model" for offline fallback. It also adds a **second data processor** for workspace content: TypeSafe directly, where ZDR is enterprise-only, or Vercel and DigitalOcean through the gateway, which offers a per-request `zeroDataRetention` flag ([Vercel changelog](https://vercel.com/changelog/typesafe-ai-jev-now-available-on-ai-gateway)). Jev should therefore be opt-in and disclosed. It should be sent typed actions and short excerpts rather than whole files, which also suits its 32k state limit and its documented weakness with large irrelevant state. Claude Haiku 5.5 or a local classifier remain alternatives for the router role, and the choice between them comes down to latency, privacy and offline operation. In Phase 0 there is no plan dataset at all, so any threshold chosen today is uncalibrated by construction. Before any Jev number appears on a card, the project should measure false-negative and false-positive rates per action type against the invoices-demo injection fixture and an adaptive red team, and show categorical badges ("instruction-like text found") rather than raw probabilities that users will read as guarantees.

## Conclusion

The description is a useful warning in its own right. AI-written summaries of new ecosystems now get the names right and the mechanics wrong, and this one stitched TypeSafe's and Vercel's APIs into code that neither accepts. The ecosystem has already adapted, with defensive packages registered against names that LLMs invent. Any integration with a four-week-old model should therefore start from the registry and the SDK source, never from a summary. Several gaps remain open: Vercel's own "auto-approve tool calls with eve and Jev" guide ([KB hub](https://vercel.com/kb/jev-from-typesafe-ai)) was not reviewed, no independent Jev benchmark exists, and the HiddenLayer result was read only through summaries.

The more lasting point concerns the threshold. A P(safe) cutoff turns a security decision into a statistics problem that no deployer can measure yet, least of all a Phase 0 project with no traffic. The asymmetry rule makes Jev something the project can adopt at little risk: it keeps the benefits (faster routing, extra flags on the card), and its worst case is the current, already-safe baseline.
